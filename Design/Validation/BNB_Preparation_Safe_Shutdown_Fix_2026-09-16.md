# BNB 가격 조회와 백엔드 안전 종료 개선

검증일: 2026-09-16 (KST)

## 확인한 원인

2026-09-15 22:41:42의 주문 준비는 직전 완료 구간인 22:41:41의 BNBUSDT 1초 종가를 조회했다. 공식 응답의 종가는 `717.77`, 거래 건수는 `0`이었다. 기존 검증기가 거래 0건을 거부하고 동일 구간을 반복 조회한 뒤, 이 실패를 `SYMBOL_FILTER_REJECTED`로 처리했다. 해당 시도의 미완료 주문 기록 저장과 거래소 주문 전송은 시작되지 않았다.

기존 종료 화면은 중지 요청 후 전체 거래 상태가 종료 상태로 바뀌기를 기다렸다. 조회 오류로 남은 주문 의도와 오류 상태를 백엔드가 직접 대조해 해제하는 절차가 없어, 화면의 대기 시간을 늘려도 안전 종료 조건을 충족하지 못했다.

가격 응답 형식의 기준은 [Binance 공식 Kline 명세](https://developers.binance.com/en/docs/catalog/core-trading-spot-trading/api/rest-api/market#klinecandlestick-data)다.

## 구현

### 주문 준비

- 정확한 직전 완료 1초 구간, 12개 필드, 양수인 유한 종가, 음수가 아닌 정수 거래 건수를 검증한다. 거래 0건인 정상 종가도 수용한다.
- 주문 전 BNB 가격 확인과 실제 개별 체결의 BNB 수수료 계산에 같은 검증기를 사용한다. 기존 거래 기록과 과거 수수료를 다시 계산하지 않는다.
- 일시적인 조회 실패는 `ORDER_PREPARATION_DEFERRED`, 잘못된 데이터는 `ORDER_PREPARATION_INVALID_DATA`, 실제 규격 위반은 `SYMBOL_FILTER_REJECTED`, 내부 오류는 `ORDER_PREPARATION_FAILED`로 구분한다.
- 저장·전송 전임이 확인된 준비 실패만 1·2·5·10·30초, 이후 30초 간격으로 재확인한다. 실제 제출 횟수를 소비하지 않으며 대기 작업을 하나만 둔다. 거래소가 더 긴 재요청 대기 시간을 지정하면 그 시간을 지킨다.
- 재시도는 현재 가격·수량·위험 조건과 신호 유효성을 다시 확인한다. 만료된 Case B/C 신호는 폐기하고 감시 상태로 돌아간다. 종료 의도가 들어오면 신규 진입과 준비 재시도를 차단한다.
- 실제 주문 전송 이후 응답이 유실된 경우에는 기존 주문 ID로 결과를 확인한다.

### 안전 종료

- `POST /v1/shutdown/prepare`는 `expected_version`과 `liquidation_confirmed`를 받아 단일 종료 준비 작업을 시작한다. `GET /v1/shutdown/prepare`는 작업 ID, 단계, 세부 작업, 버전, 차단 사유와 재시도 가능 여부를 반환한다.
- 단계는 `checking`, `settling_orders`, `liquidating`, `ready`, `blocked`다. 화면과 실시간 연결 없이 별도 API로 진행을 조회한다. Python 계약과 생성 TypeScript 계약을 함께 갱신했다.
- 신규 거래를 차단하고 진행 중 작업자·구독을 정리한 뒤, 종료 담당 작업만 계좌와 주문을 대조한다. 네트워크 요청과 작업자 종료 대기는 전역 잠금 밖에서 수행한다.
- 미완료 주문 기록, 전송 근거, 실제 주문·체결·잔고를 대조한다. 앱 소유 미체결만 기존 취소·결과 확인 경로로 정리하며, 청산은 사용자가 동의했을 때만 한다.
- 거래 파일을 새로 읽어 별도 포지션에 재생하고 현재 포지션·잔여 ETH 장부와 비교한다. 기존 Earn 잔여 대조 규칙을 사용한다. 설명되지 않는 주문·체결·잔고·기록 또는 소유권 문제는 종료를 차단한다.
- 전송 전 실패가 남긴 의도는 해당 주문의 전송 근거와 미완료 기록이 없음을 확인한 뒤에만 해제한다. 작업자·화면·시세 오류 기록은 보존하며 자동매매를 재개하지 않는다.
- 120초 기한을 별도 감시한다. 기한이 지나면 마지막 단계와 차단 사유를 게시하고, 늦게 완료된 작업이 추가 주문이나 종료 승인을 진행하지 못하게 한다. 진행 중인 네트워크 요청을 강제로 끊어 성공으로 간주하지 않는다.
- `ready` 이후 기존 `POST /v1/shutdown`에서 버전, 노출, 미완료 기록과 저장 상태를 다시 검증한다. 저장·자원 정리·실제 백엔드 정상 종료를 확인한 다음 창을 닫는다.
- 일반 종료, 창 닫기, Cmd+Q, 복구 화면 종료가 같은 준비 API를 사용한다. 응답 유실에는 같은 요청과 작업 ID를 유지한다. 네이티브가 확인한 프로세스 종료 이벤트와 창 닫기 경로도 유지한다.

### 기존 고아 프로세스 운영 복구

사용자의 기존 백엔드 종료 요청에 따라, 주문 권한 없는 클라이언트와 기록 복사본으로 실제 계좌를 대조했다. 열린 포지션·미체결 주문·미완료 기록이 없고 기존 잔여 ETH `0.00009600`과 장부가 일치했다. 기존 프로세스가 부모 연결 유실로 신규 주문을 차단한 상태임을 확인하고 원본 기록을 백업한 뒤 PID 50382에 SIGTERM을 전송했다. PID 50382와 래퍼 PID 50381 모두 종료됐다. 이는 새 종료 API의 정상 종료 접수 결과가 아닌 운영자 복구 절차다.

종료 후 실제 계좌를 다시 대조해 같은 결과를 확인했고, OS 잠금을 독점 획득한 상태에서 소유권 기록을 `ORPHANED`에서 `RELEASED`로 갱신했다. 거래·미완료 주문·잔여 ETH 파일의 해시는 전후 동일하며 주문·취소·자산 이동은 수행하지 않았다. 검증 및 복구 근거는 상세 검증 폴더의 `operator-*.json`과 `before-operator-recovery/`에 보존한다.

개발 포트 5173이 비어 있고 프로젝트 지정 pnpm 11.16.0을 실행할 수 있음을 확인했다. 새 앱은 자동 실행하지 않았다. `UI` 디렉터리에서 `pnpm desktop:dev`로 수정된 소스를 실행할 수 있다.
