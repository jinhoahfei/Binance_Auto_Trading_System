# 강제매도 후 종료 실패 수정 및 검증

작성일: 2026-09-27

## 적용 내용

- 기존 `clear_pending_order()` 수정을 유지했다. 매도 전 미제출 주문 정리와 매도 후 최종 정리는 `pending_exit_reason`, `pending_return_state`를 함께 정리한다. 상태 검증은 복구 자원 폐기 전에 수행한다.
- 종료 중 상태가 바뀌거나 자원 정리에 실패해도 인증된 종료 기준 조회와 재준비를 허용한다. `SHUTTING_DOWN` 또는 `CLOSED`가 되어도 일반 거래 명령의 준비 상태는 열리지 않는다.
- 종료 자원의 요청·진행·완료·실패를 내부에 기록한다. `CLOSED` 표시만으로 `accepted=true`를 만들지 않는다. 구독 정리에 실패하면 실제 handle을 보존하며, 완료한 자원은 중복 처리하지 않는다.
- 작업 및 타이머 시작 실패에서 작업 소유권을 해제한다. 이미 실행 중인 작업은 시간초과 표시만으로 해제하지 않는다. 잠금, 작업자 회수, 네트워크, 구독 정리에 같은 종료 예산의 남은 시간을 전달한다.
- 이미 진행 중인 HTTP 명령이 잠금을 양보하고 외부 응답을 기다리는 경우, 해당 명령이 끝나기 전에 종료 준비가 별도 청산을 시작하지 않게 한다. 최종 종료를 기다리는 요청에는 각 요청 세대의 독립 결과와 제한시간을 적용한다.
- 실제 백엔드 종료가 확인된 후 창 닫기 구독을 해제하고 창 제거를 최대 세 번 시도한다. 모두 실패해도 사용자의 다음 닫기를 가로채지 않으며, 창 재시도는 백엔드 종료나 매도를 다시 요청하지 않는다.
- 자원별 정리와 작업 시작 실패에는 단계·자원·작업 ID를 기록한다. 원문 예외나 비밀값 대신 기존 안전한 예외 진단 형식을 유지한다.

## 준수 조건

**CODING_CONVENTIONS.md를 준수했다. 기존 UI 화면을 변경하지 않았다.** 레이아웃, 색상, 글꼴, 문구, 버튼, 모달 구성은 그대로다. 변경한 UI 제품 코드는 창 수명을 처리하는 hook과 runtime 두 파일이며, 나머지 하나는 해당 테스트다.

외부 API 응답 구조와 저장 형식은 유지한다. 데이터 마이그레이션, 잔고·주문·저장 검증 생략, 강제 프로세스 종료는 없다. 모의 거래소와 임시 저장소로 검증했고 실주문은 실행하지 않았다.

## 자동 검증

| 변경 공백 검사 | 오류 없음 |

최초 제한 환경 실행에서 로컬 포트와 프로세스 조회가 차단된 테스트는 해당 기능을 허용한 환경에서 다시 통과했다. 최종 결과는 `backend-full-verified.log`, `ui-full.log`와 `ui-process-verified.log`, `native-tests-verified.log`에 기록했다. 전체 테스트 출력의 릴리스 감사·장기 운전 증빙 GAP은 기존 테스트 fixture 출력이며 이번 종료 회귀 통과와 별개다.

실제 자식 프로세스의 모의 거래소 시나리오에는 미제출 매도 사유·복귀 상태, 완료 BUY의 남은 복구 표시, 강제매도, 기록 저장, 인증된 HTTP 종료, 종료 승인 ACK, 종료 코드 0 및 저장소 소유권 RELEASED 확인을 포함한다. 매도 후 첫 자원 정리를 실패시키는 시나리오도 추가했으며, 재시도 후 기록은 BUY·SELL 각 1개다.

기존 테스트로 부분 체결·취소 응답 유실·매도 응답 유실·저장 실패·동시 종료 요청을 검증했고, 새 테스트로 상태 변경 후 재준비, 정리 실패 후 거짓 성공 방지, Thread/Timer 시작 실패, 잠금 시간초과, 늦은 응답의 단일 소유권, 통지·스케줄러 정리 실패와 창 제거 실패를 검증했다.

## 화면 보존

- 작업 시작 시 저장한 UI 소스 280개 해시와 대조했다. 변경은 내부 창 처리 두 파일과 그 테스트뿐이다. `ui-source-preservation.json` 참조.
- 수정 전 HEAD와 수정 후 소스로 Storybook을 각각 새로 빌드했다. 기존 기준 이미지와 제품 화면 소스를 갱신하지 않았다.
- 종료 오류 모달, 종료 준비 진행 화면, 잔고 확인 대시보드, 실시간 지표 화면의 전후 4쌍을 비교했다. 모든 이미지의 바이트와 RGB 픽셀이 동일하다. 캡처 이미지 크기는 1404×1024다.
- 진행 화면의 애니메이션은 두 임시 정적 빌드에만 같은 정지 조건을 적용해 비교했다. 제품 CSS와 Storybook 원본에는 변경이 없다.
- 증거: `ui-captures/capture-state.json`, `ui-captures/pixel-comparison.json` 및 8개 캡처.

## 패키지 및 설치 확인

최종 소스로 macOS 앱을 빌드했다. 앱에 포함된 Python 모듈 127개가 현재 소스의 컴파일 결과와 모두 일치한다. production 소스로 우회하는 import를 금지한 상태에서 앱 내부 모듈로 종료 관련 테스트 99개를 실행해 통과했다. 이 중 실제 자식 프로세스 네 가지도 동일한 앱 내부 모듈을 사용했다.

로컬 사용을 위한 ad-hoc 앱 서명을 적용하고 `codesign --verify --deep --strict` 검증을 통과했다. `/Applications/Binance Auto Trader.app`을 검증한 새 앱으로 교체했으며, 설치본의 모든 파일 5개가 빌드와 SHA-256 기준으로 일치한다. 테스트한 sidecar와 설치된 sidecar의 해시도 일치하고, 설치본 내부 모듈 127개를 다시 소스와 대조했다.

이전 설치본은 `previous-installed-app/`에 보존했다. 기존 설치본에 직접 원인의 `clear_pending_order()`와 새 자원 정리 모듈이 없었다는 확인은 `installed-before.json`에 있다. 새 앱의 결과는 `bundle-verification.json`, `bundle-tests.log`, `installation-verification.json`에 기록했다.

실거래 계정으로 앱을 새로 실행하거나 현재 실행 중인 기존 디버그 sidecar를 종료하지 않았다. 새 코드의 적용은 새 앱 실행 시점부터다.

실제 운영 계정·실거래를 포함한 수동 데스크톱 시험은 수행하지 않았다. 창 제거 실패와 사용자의 다음 닫기는 창 제어 포트를 모의한 UI 테스트로 검증했다.
