# 전체 구동 기간 Case B 진입 여부 분석

분석일: 2026-09-22. 모든 시각은 한국 시간(KST), 가격·금액은 USDT다.

**확정 결론: 2026-09-18 10:03:38에 명세상 Case B 매수 조건을 충족했고, 앱도 이를 인식해 매수 요청을 만들었다. 그러나 기존 잔여 ETH를 주문 예산에서 먼저 빼지 않는 수량 산정 때문에 총 보유 한도 검사에서 차단되어 실제 주문·체결로 이어지지 않았다. 같은 기회에서 31번 후보를 만들었으며 독립된 진입 기회는 1건이다.**

다른 저장된 구동 구간과 별도 검토한 중단 구간에서 추가로 확정할 수 있는 Case B 진입 누락은 확인하지 못했다. 실제 Case C 보유를 제거하거나 정상 청산됐다고 가정한 전체 대체 매매 시뮬레이션은 하지 않았다.

## 4. 왜 실제 매수하지 못했는가

당시 단건 주문 한도와 총 보유 한도는 각각 10 USDT였다. 새 주문량 계산은 단건 한도만 고려했지만, 뒤의 위험 검사는 이미 남아 있던 잔여 ETH까지 합쳤다.

| 최초 시도의 항목 | 금액 |
|---|---:|
| 새 매수 후보: 0.0040 ETH × 2,446.45 | 9.7858000 |
| 기존 잔여 원금: 0.000096 ETH × 2,446.45 | 0.2348592 |
| 예상 합계 | **10.0206592** |
| 총 보유 한도 | **10.0000000** |
| 초과분 | **0.0206592** |

원본 차단 사유는 `RISK_POSITION_NOTIONAL_EXCEEDED`다. 최종 위험 검사는 설정대로 작동했으며, 앞 단계가 남은 예산에 맞춰 주문량을 줄이지 않은 것이 문제다. 준비한 0.0040 ETH 주문은 이 한도에서 그대로 전송하면 안 되는 수량이었다.

잔여 원금을 먼저 빼면 가용 총예산은 9.7651408이고, 수량 단위로 내리면 **0.0039 ETH**다. 그 경우 새 주문 9.541155 + 잔여 0.2348592 = **9.7760142**로 총 보유 한도는 통과한다. 다만 당시 거래소 최소 주문 금액이 기록에 없어 **이 수량이면 반드시 실체결됐다고 단정할 수는 없다.**

31회는 같은 회복 신호에 대한 반복 후보다. 거래소가 매수 주문 31건을 거절한 것이 아니며, 로컬 위험 검사에서 전송 전에 차단됐다.

## 7. 명세 해석과 검증의 범위

- 새 30분봉 하단 재접촉으로 기존 이벤트를 종료하는 규칙은 명세 §5.6에 있다. 신호 후 3시간을 무조건 유지하는 단독 전략과 통합 규칙을 혼용하면 결과가 달라진다. 이번 실제 WAIT_PULLBACK에서는 새 접촉으로 신호가 지워진 기록은 없었다.
- EMA slope 상세 산식은 명세에 빠져 있다. 실제 코드 산식으로 공개 봉 재계산은 로그와 일치했지만 설계자 개인의 별도 구현까지 같다고 검증한 것은 아니다.
- 명세 §5.10의 상단 접촉 런타임 종료와 9/17 이후 현 코드의 다음 하단 감시 복귀는 다르다. 이 문서 불일치는 별도로 존재하나, 9/18 10:03의 예산 차단 원인은 아니다.
- 매수 신호가 유효했다는 사실은 실제 체결 보장이나 이후 수익 보장을 뜻하지 않는다. 주문 한도·수량 단위·최소 주문금액은 별도의 실행 조건이다.
- 공개 1분봉으로 시장의 모든 틱 순서를 복원할 수는 없다. 중단 구간은 저장된 시세 업데이트, 동적 밴드 조건, 확정봉 조건으로 판정 가능한 범위만 결론 냈다.
