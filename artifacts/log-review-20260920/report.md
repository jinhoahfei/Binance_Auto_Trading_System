동일 주문에 대해 앱이 결과를 처리한 순서는 다음과 같다.

실제 거래 내역 파일에는 해당 매수가 정상적으로 존재한다. 주문 복구 기록에도 `PREPARED → SUBMITTED → TERMINAL → HISTORY_COMMITTED → REMOVE`가 모두 남아 있다. 따라서 오류 이름만 보고 “매수 내역을 저장하지 못했다”라고 해석하면 부정확하다.

코드는 완료된 주문에 대해 뒤늦은 `NEW`와 동일한 완료 알림은 무시하지만, 이미 반영한 체결 일부를 담은 `PARTIALLY_FILLED`는 이 처리에서 빠진다. 그 결과 완료 후 제거한 대기 주문 기록을 다시 갱신하려고 한다. 저장소는 대기 주문이 없다는 예외를 발생시키고, 상위 코드는 이를 포괄적으로 `HISTORY_PERSISTENCE_FAILED`로 분류한다.

동일한 결과 도착 순서를 외부 연결 없는 가짜 거래소와 임시 기록 파일로 재현했다. 완료 응답과 늦은 `NEW`까지는 `running`이었고, 늦은 부분 체결을 넣자 실제 로그와 같은 `reconciliation_required`가 됐다. 재현에서 확인한 예외는 `ValueError: pending-order transition requires an active pending order`다. 거래 내역은 계속 1건, 대기 주문은 0건, 보유량도 그대로였다. 늦은 완료 알림에서도 같은 오류가 재발했다.

운영 로그에는 원본 예외 메시지가 남아 있지 않다. 따라서 이 예외 문구를 운영 로그에서 직접 읽은 것은 아니다. 운영의 이벤트 순서·저장된 기록·현재 코드 경로가 일치하고, 격리 재현에서도 같은 상태 전이가 발생한 것을 근거로 원인을 특정했다.

## 왜 시세는 보이는데 자동 매도가 멈췄나

`reconciliation_required`에서는 새 시세가 들어와도 전략 평가 이벤트를 만들지 않는다. 최신 시세 로그와 주기적인 실행 상태 기록은 계속 증가하지만, 전략 지표와 보유 시간 비교값은 06:22:48 시점에 머물러 있다.

마지막 보유 평가에서 익절 구간, 손절 조건, 보유 1시간 조건, 상단 도달 조건은 모두 거짓이었다. 하지만 이후의 조건 변화는 평가되지 않았다. 특히 Case C에는 보유 3,600초 조건이 있으므로 07:22:48경부터 시간 청산 조건을 평가해야 했지만, 중단 상태 때문에 해당 평가 및 매도 기록이 없다. 이후 손절이나 익절 조건이 실제로 언제 충족됐는지는 별도 시장 재생 분석을 하지 않았으므로 단정하지 않는다.

현재 로그의 `recovery.phase: resumed`는 04:01 시세 장애 복구 이력이 남은 값이다. 이것만 보고 거래가 재개됐다고 판단하면 안 된다. 최종 세션 상태는 `reconciliation_required`, `command_enabled: false`, `has_open_position: true`다. 시세 연결 장애에 대한 자동 복구 경로는 주문·기록 오류를 자동 해제하지 않는다.
