# 주문·연결 복구 결함 수정 실행 보고서

기준 계획: [주문 오류·연결 단절·실시간 판정 중단 예방 수정 계획](order-connection-resilience-plan-20260922.md)  
검증일: 2026-09-27  
범위: 현재 작업 폴더의 실행 코드와 주문 없는 로컬 회귀 검증. 실제 거래소 호출, 계좌·키 설정 변경, 실행 중 앱 재시작은 수행하지 않는다.

## 중단 지점 확인

9월 22일 작성한 R1~R5 수정과 회귀 테스트가 작업 폴더에 보존되어 있었다. 마지막 중단 시점은 R1의 주문 직전 권한 재검사와 공통 시간 예산을 추가한 뒤 전체 회귀 검증을 시작한 단계였다. 당시 임시 전체 테스트 로그는 남아 있지 않아 성공으로 간주하지 않고 현재 파일에서 재실행했다. 기존 `artifacts/case-b-*`의 사용자 변경은 유지했다.

## 구현 결과

| 항목 | 변경 내용 |
| --- | --- |
| R1: 주문·복구 대기 격리 | 하나의 실행 소유자가 주문·STM·결과 반영 순서를 유지한다. 외부 REST와 계좌 구독 대기 중에는 재진입 application lock 전체를 양보하고 결과 반영 전에 복원한다. 상태 조회와 시세 관측은 진행하며 다른 주문 effect는 추월하지 못한다. |
| R1: 제출 권한 | 실제 전송 시작 기록과 최신 권한 검사를 같은 잠금으로 묶었다. 정확한 Order 객체·세션·복구 세대·계좌 readiness를 대조하고 BUY에는 긴급 정지·잔액 버전·위험 정책 변경도 검사한다. STOP 예약은 요청별로 회수하고 기존 청산을 중복 STOP 때문에 차단하지 않는다. 전송을 시작한 주문의 늦은 결과는 버리지 않는다. |
| R1: 시간·조회 제한 | 중첩 외부 작업은 하나의 30초 단조 시계 예산을 상속한다. REST별 timeout과 body 조각의 대기 시간을 잔여 예산으로 줄인다. snapshot은 서버별 최대 4개 요청만 수락하고 잠금 획득을 1초 내에 끝내거나 재시도 가능한 503 `BACKEND_NOT_READY`/`SNAPSHOT_BUSY`를 반환한다. |
| R2: 진단 저장 | production 진단을 용량 1,024 queue와 단일 writer로 분리했다. 원래 관측 시각·순서·민감정보를 제거한 payload를 복사하고 초과·실패·미기록 수를 집계한다. 종료 대기는 1초다. 주문 저널과 거래 이력의 fsync는 그대로 유지한다. |
| R3: 시세·장애 통지 | 공개 시세를 용량 제한 FIFO dispatcher로 전달한다. 초과 시 해당 연결을 닫고 기존 복구 경로로 넘기며 봉 종료 이벤트를 합치지 않는다. 장애 통지는 별도 단일 worker에서 중복을 병합하고, 실제 transport readiness는 통지 완료를 기다리지 않고 닫는다. 구독 생성 세대로 늦은 이전 연결의 통지가 새 연결의 복구 요청을 덮어쓰지 못하게 한다. |
| R4: 프론트 재연결 | 최초 단절은 즉시 복구하되 반복 close·gap·resync는 기존 1·2·5·10·30초 간격을 사용한다. 정상 수신이 60초 유지된 뒤 예산을 초기화한다. snapshot·socket·재시도 timer는 각각 하나만 유지한다. |
| R5: 확정 미전송 | adapter의 정확한 준비·전송 시작 이력으로 POST 이전 만료·권한 취소만 확정 미전송으로 구분한다. `NOT_SUBMITTED_CONFIRMED`를 pending schema v5로 fsync한 뒤 정리한다. 기존 기록은 v4로 유지하고 v1~v5를 읽는다. 이미 전송했거나 증거가 모호하면 같은 ID 조회를 유지하며 재시작 후 메모리 부재를 미전송 증거로 사용하지 않는다. |

## 검증 원칙과 제한

- **`CODING_CONVENTIONS.md`를 계속 준수한다.** 새 함수·클래스 설명, 이름, 들여쓰기와 공백을 확인하고 기존 architecture 검사를 유지한다.
- **기존 UI 화면은 변경하지 않는다.** 수정 대상은 `BackendUiAdapter.ts`와 테스트다. JSX, CSS, 디자인 토큰, 화면 문구, 폰트, 아이콘, 자산과 사용자 조작 화면은 보존한다. 기존 시각 기준과 허용 오차도 변경하지 않는다.
- 실제 전송이 시작된 주문의 시간 초과는 결과 미확정으로 처리한다. future timeout으로 주문 worker를 방치하거나 별도 재전송 worker를 만들지 않는다.
- 30초는 후속 요청과 응답 body 조각 사이에서 공유하는 작업 예산이다. **현재 urllib 내부의 DNS 조회·연결·TLS·헤더 및 chunked framing 수신을 OS 수준에서 강제 중단하는 절대 30초 보장은 아니다.** 이 구간은 transport의 기존 socket 제한에 의존한다. 이런 지연 중에도 관측 잠금은 양보하며, 작업이 돌아오면 남은 예산을 검사한다. 계획의 절대 마감 시간 요구 중 이 부분은 제한으로 남는다. 엄격한 전체 상한을 위해서는 DNS resolver와 HTTPS 전송 계층을 별도로 교체하고 취소·POST 경합을 검증해야 한다. 이번 수정에서는 요청을 방치하는 timeout worker를 추가하지 않았다.
- 로컬 회귀는 장애 경계의 동작을 검증한다. 실제 운영 장애의 원인을 로그로 확정하거나 실거래·장시간 운영 안정성을 입증한 결과로 해석하지 않는다.

실제 worker의 재진입 잠금 아래에서 주문 준비와 진단 sink를 동시에 정지시켜도 상태·시장 관측과 heartbeat 진단 기록이 반환했다. queue 초과 계수가 증가하고도 fake 주문은 한 번만 제출되어 이력 한 건으로 반영됐다. 별도 제출 경계 테스트에서 STOP·긴급 정지·정책 변경·잔액 갱신·계좌 단절 전 POST 차단, 전송 뒤 늦은 체결의 단일 반영, 중복 STOP의 동일 응답과 청산 한 번, 예약 후 세션 변경의 정리까지 확인했다.

처음 실행한 backend suite의 로컬 포트 관련 오류는 sandbox의 bind 제한이었다. 로컬 통신을 허용한 전체 재실행에서 위 결과를 얻었다. 테스트 과정에서 진단 sink 오류와 출시 준비도 GAP를 주입하는 기존 fixture의 출력은 유지했으며, 출시 준비도 인증으로 해석하지 않는다.
